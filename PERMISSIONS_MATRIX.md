# Матрица прав доступа

Статус: согласованная целевая модель, реализация по этапам.

## 1. Принципы

1. Доступ разрешается явно. Если разрешение не задано, действие запрещено.
2. Сервер проверяет право на каждый GET, POST, скачивание и экспорт.
3. Скрытие кнопки в интерфейсе не заменяет серверную проверку.
4. Право на действие и область доступных данных проверяются отдельно.
5. Физическое удаление критичных данных доступно только `superadmin`.
6. Операционные роли используют деактивацию, архивирование и soft delete.
7. Изменения ролей, прав и чувствительных данных записываются в Audit Log.

## 2. Роли

| Роль | Назначение |
|---|---|
| `superadmin` | Технический владелец системы: разработка, отладка, безопасность и неограниченный доступ |
| `hr_lead` | Руководитель HR-проекта: все HR-регионы и управленческий контроль без технического администрирования |
| `hr_manager` | Операционный HR-менеджер: работа только в закреплённых регионах |
| `economist` | Финансовая работа только в закреплённых регионах |
| `brigadier` | Работа только с закреплёнными магазинами |
| `employee` | Работа только с собственными данными |

### Переходное правило

До завершения миграции текущие пользователи с `role = "admin"` или `is_admin = True` считаются `superadmin`. Новым пользователям роль `admin` не назначается.

## 3. Области данных

| Код | Область |
|---|---|
| `ALL` | Все данные системы |
| `HR_ALL` | Все HR-данные по всем регионам |
| `CITIES` | Только закреплённые города |
| `STORES` | Только закреплённые магазины |
| `OWN` | Только данные текущего сотрудника |
| `SUMMARY` | Только агрегированные показатели без персональных финансовых деталей |
| `NONE` | Доступ запрещён |

## 4. Уровни действий

| Код | Действие |
|---|---|
| `V` | Просмотр |
| `C` | Создание |
| `U` | Изменение |
| `A` | Подтверждение, отклонение или обработка |
| `X` | Экспорт или скачивание |
| `D` | Деактивация, архивирование или soft delete |
| `HD` | Физическое удаление |
| `S` | Изменение настроек модуля |
| `F` | Финальная финансовая операция: отправка или закрытие периода |

Обозначение `V/C/U@CITIES` означает действия только в закреплённых городах.

## 6. Ограничения управления пользователями

| Исполнитель | Кого может создавать и редактировать | Какие роли может назначать |
|---|---|---|
| `superadmin` | Всех пользователей | Все роли |
| `hr_lead` | HR Lead, HR Manager, Brigadier, Employee | `hr_lead`, `hr_manager`, `brigadier`, `employee` |
| `hr_manager` | Brigadier и Employee только в своих городах | `brigadier`, `employee` |
| `economist` | Никого | Никакие |
| `brigadier` | Никого | Никакие |
| `employee` | Только разрешённые поля собственного профиля | Никакие |

Только `superadmin` может назначать роль `superadmin`, изменять технические области доступа, выполнять физическое удаление пользователя и менять системные настройки авторизации.

## 7. Критичные финансовые ограничения

1. Только `superadmin` закрывает payroll-период.
2. `economist` формирует, корректирует, фиксирует и передаёт табель в оплату только по своим городам.
3. `hr_lead` видит и экспортирует payroll без права изменения сумм.
4. `hr_manager` видит и экспортирует payroll, видит ставки и ЛМК только в назначенной области, без права изменения.
5. `brigadier` и `employee` не видят финансовые расчёты, кроме явно разрешённой собственной истории выплат сотрудника.

## 8. Целевая модель областей доступа

Текущее поле `User.economist_stores` фактически хранит города и не подходит для новых ролей. Целевая модель должна хранить области отдельно от роли.

```text
UserAccessScope

id
user_id
scope_type: city / store
scope_value
created_by
created_at
is_active
```

До миграции `economist` продолжает использовать `User.economist_stores`, `brigadier` — `User.brigadier_store`, а новые роли не выдаются реальным пользователям.

## 9. Обязательные события Audit Log

- создание, изменение, блокировка и деактивация пользователя;
- изменение роли пользователя;
- назначение или удаление области доступа;
- вход и неуспешная попытка входа;
- попытка запрещённого чувствительного действия;
- загрузка пользователей и смен;
- просмотр или скачивание документа сотрудника;
- проверка, отклонение и архивирование документа;
- изменение реквизитов;
- изменение ставок и финансовых корректировок;
- фиксация, передача и закрытие payroll;
- изменение системных настроек;
- физическое удаление данных.

## 10. Текущие разрывы

1. В системе отсутствуют роли `superadmin`, `hr_lead` и `hr_manager`.
2. `is_admin = True` является универсальным пропуском во многие модули.
3. Роль `admin` одновременно означает технического администратора и операционного руководителя.
4. Области доступа хранятся в полях, привязанных к конкретным ролям.
5. Проверки доступа распределены по разным dependencies и локальным helpers.
6. Часть разделов использует общий `require_economist_user` без проверки конкретного разрешения.
7. UI-маршрут и серверное действие не всегда описываются единым разрешением.
8. Для большинства модулей отсутствуют автоматические тесты матрицы прав.

## 11. План внедрения

### RBAC-1. Совместимый фундамент

- добавить константы ролей и нормализацию старого `admin` в `superadmin`;
- добавить каталог разрешений;
- создать `UserAccessScope`;
- реализовать `require_permission`, `can_access_city`, `can_access_store`, `can_access_own_record`;
- не менять фактические права существующих пользователей.

### RBAC-2. Технические и критичные разделы

- защитить `/docs`, `/redoc`, `/openapi.json`, debug и maintenance;
- защитить управление ролями и пользователями;
- защитить payroll close, hard delete и системные настройки;
- добавить Audit Log запрещённых чувствительных действий.

### RBAC-3. HR-контур

- внедрить `hr_lead` и `hr_manager`;
- перевести пользователей, документы, реквизиты и модуль «Сотрудники»;
- применить области `HR_ALL` и `CITIES`;
- добавить интерфейс назначения регионов.

### RBAC-4. Финансовый и операционный контур

- перевести payroll, корректировки, ставки, ЛМК, отчёты и аналитику;
- перевести `economist` на `UserAccessScope`;
- перевести `brigadier` на магазинные области.

### RBAC-5. Тестирование и включение

- добавить параметризованные тесты для каждой роли, области и действия;
- проверить прямые POST-запросы и скачивание файлов;
- провести ручную проверку под каждой ролью;
- создать реальных `hr_lead` и `hr_manager`;
- после подтверждения прекратить назначение старой роли `admin`.

## 12. Критерии готовности

- каждый маршрут связан с явным разрешением;
- каждый запрос к персональным данным ограничен областью пользователя;
- UI не показывает недоступные действия;
- прямой запрос к скрытому действию также запрещён;
- изменение роли или области доступа отражается в Audit Log;
- текущий владелец системы сохраняет полный доступ;
- HR Lead не имеет доступа к техническим функциям;
- HR Manager не видит данные чужих регионов;
- Economist не видит финансовые данные чужих регионов;
- Brigadier не видит чужие магазины;
- Employee видит только собственные данные.

## 13. Инвентаризация текущей реализации

На дату составления документа приложение содержит 165 зарегистрированных маршрутов:

- Admin: 31 GET и 54 POST;
- Economist: 23 GET и 38 POST;
- Employee, Brigadier и общие маршруты: остальные;
- текущие роли: `admin`, `economist`, `brigadier`, `employee`;
- текущие общие зависимости: `require_admin_user`, `require_economist_user`, `require_brigadier_user`.

### Уже защищено корректно относительно текущей модели

- `/docs`, `/redoc`, `/openapi.json` требуют текущий admin-доступ;
- `/debug/shifts-count` и `/admin/fix-phones` требуют admin-доступ и отключены без `ENABLE_MAINTENANCE_ROUTES=1`;
- скачивание документа сотрудника проверяет доступ пользователя к конкретному документу;
- кабинет сотрудника загружает документ только от имени текущего сотрудника;
- economist-маршруты документов используют область доступных сотрудников;
- закрытие payroll доступно только текущему admin;
- модуль «Сотрудники» проверяет города экономиста и в GET, и в действиях.

### Приоритетные разрывы

| Приоритет | Разрыв | Требуемое действие |
|---|---|---|
| `P0` | `/admin/payroll/runs/send` допускает `economist`, но не проверяет принадлежность run доступным городам | До внедрения новых ролей добавить проверку области run либо разделить admin/economist actions |
| `P0` | `is_admin=True` и `role="admin"` дают универсальный доступ | Ввести совместимую функцию `is_superadmin`, затем прекратить прямые проверки флага в модулях |
| `P1` | Текущий admin может физически удалить пользователя | После RBAC-1 закрепить hard delete только за `superadmin`, остальным дать деактивацию |
| `P1` | Economist имеет маршруты физического удаления юрлица | Оставить economist только деактивацию; hard remove закрепить за `superadmin` |
| `P1` | Economist может создавать, изменять и деактивировать типы документов | После ввода HR-ролей оставить economist просмотр типов документов |
| `P1` | Проверки ролей распределены между общими dependencies и локальными helpers | Перевести чувствительные маршруты на единый каталог permissions |
| `P2` | Maintenance-операция изменения телефонов реализована как GET | После RBAC-2 заменить на POST с явным подтверждением и Audit Log |
| `P2` | Нет системной блокировки учётной записи | Добавить `is_active`/`disabled_at` и запрет входа заблокированным пользователям |
| `P2` | Не все скачивания и просмотры чувствительных данных журналируются | Расширить Audit Log по перечню из раздела 9 |

## 14. Первый согласованный пакет реализации

Первым изменением предлагается выполнить `RBAC-1` без изменения фактических прав существующих пользователей:

1. Добавить роли `superadmin`, `hr_lead`, `hr_manager` в нормализацию ролей.
2. Считать старые `admin` и `is_admin=True` эквивалентом `superadmin`.
3. Создать централизованный каталог разрешений в отдельном модуле.
4. Добавить модель `UserAccessScope` и безопасное создание таблицы.
5. Создать helpers областей доступа с fallback на старые поля.
6. Добавить параметризованные тесты ролей и областей.
7. Исправить P0-проверку передачи payroll run экономистом.
8. Пока не показывать новые роли в production-формах создания пользователей до завершения тестирования HR-контура.

Такой порядок создаёт техническую основу, закрывает найденный финансовый риск и не меняет привычный доступ действующих пользователей.

## 15. Статус реализации

### Реализовано в RBAC-1

- добавлены роли `superadmin`, `hr_lead`, `hr_manager` в нормализацию;
- старые `admin` и `is_admin=True` совместимо считаются `superadmin`;
- создан централизованный каталог permissions и helpers областей;
- создана таблица `user_access_scopes`;
- добавлен fallback на старые поля областей;
- закрыт P0 отправки смешанного payroll run экономистом.

### Реализовано в RBAC-2

- `/docs`, `/redoc`, `/openapi.json` закреплены за `superadmin`;
- maintenance/debug закреплены за `superadmin`;
- изменяющий маршрут `/admin/fix-phones` переведён с GET на POST;
- управление пользователями и смена паролей закреплены за `superadmin` до внедрения HR-контура;
- физическое удаление пользователя закреплено за `superadmin`;
- удаление и закрытие payroll run закреплены за `superadmin`;
- физическое удаление юрлица закреплено за `superadmin`;
- физическое удаление ставки закреплено за `superadmin` до появления soft delete;
- запрещённые чувствительные действия записываются как `permission_denied`;
- недоступные hard-delete кнопки скрыты в интерфейсе экономиста.

### Реализовано в RBAC-3

- добавлен отдельный `/hr` кабинет для `hr_lead` и `hr_manager`;
- после входа обе HR-роли направляются в HR-кабинет;
- `hr_lead` видит все регионы и управляет назначением городов HR-менеджерам;
- `hr_manager` видит только назначенные города;
- добавлены HR-маршруты сотрудников, документов, реквизитов и ограниченных HR-отчётов;
- GET, POST и скачивания в HR-модуле сотрудников ограничены областью города;
- документы и реквизиты HR-менеджера ограничены сотрудниками назначенных городов;
- изменения городов сохраняются в `user_access_scopes` и Audit Log;
- старое поле `economist_stores` синхронизируется как переходная совместимость;
- новые роли доступны в формах создания и редактирования пользователей.

Ограничения текущего этапа:

- HR-реквизиты пока доступны только для просмотра;
- управление типами документов из HR-кабинета пока не предоставлено;
- создание подчинённых учётных записей HR-ролями будет реализовано отдельным этапом.

### Следующий этап

`RBAC-5`: довести действия HR-контура до согласованной матрицы, расширить Audit Log и перевести оставшиеся локальные проверки ролей на единый каталог permissions.

### Реализовано в RBAC-4

- HR Lead: просмотр и экспорт payroll по всем регионам без финансовых действий;
- HR Manager: просмотр и экспорт payroll, просмотр ставок и ЛМК в назначенной области;
- область HR Manager поддерживает города и необязательное сужение по магазинам;
- без выбранных магазинов доступны все магазины назначенных городов;
- ограничение городов и магазинов применено к HR-модулям и payroll;
- HR Lead и HR Manager могут безопасно сбрасывать пароли только сотрудникам и бригадирам;
- новые экономисты без явно заданных городов получают все существующие города.
