# ТЗ П5.2: тур кадровика и право кадровика править карточки сотрудников

**Проект:** work-system · **База:** `main` после `34e559f` · **Дата:** 15.10.2026
Ветка `feat/p5-2-hr-clerk`, коммиты по блокам A–B. Расчёты не трогаем.

## Блок A — кадровик правит карточки сотрудников

Решение владельца: специалист по кадровому учёту ведёт карточки линейного персонала — правит личные данные, добавляет документы и заполняет их реквизиты.

1. **Что можно.** Роль `hr_clerk` редактирует на `/admin/users` (и в карточке из `/hr/employees`) только пользователей с ролью `employee` и только их личные поля: ФИО, дата рождения, пол, гражданство, должность, ИНН, «студент». Документы сотрудника — загрузка, карточка документа, реквизиты документа, проверка — уже доступны по `documents.manage` и не меняются.
2. **Что нельзя.** Роль, телефон-логин, пароль и кабинет, закреплённый ТМ, реквизиты выплат, удаление пользователя — у кадровика поля только для чтения или скрыты, сервер их игнорирует. Пользователи других ролей открываются только на просмотр.
3. **Как сделать.** Отдельное право `users.edit_personal` (кадровику, руководителю и суперадмину). В `update_user`: при наличии только этого права (без `users.manage`) — проверка, что цель имеет роль `employee`, и сохранение только полей из белого списка; прочие параметры запроса отбрасываются без ошибки. Аудит — `user_updated` с изменёнными полями. `can_manage_role` и защита ролей из П4.8 не меняются.
4. **Тесты:** кадровик меняет ФИО и дату рождения сотрудника → сохранено; присланные им же `role`, `phone`, `tm_id`, `password` → проигнорированы; кадровик открывает ТМ или экономиста → только просмотр, POST → 403; аудит пишет изменённые поля.

## Блок B — тур кадровика

Текст — **дословно** из `docs/tours/P5_3_hr_clerk_tour_draft.md` (владелец положит файл с правками). Решения владельца: в приветствии роль называется «специалист по кадровому учёту»; шаг про сотрудников — см. п. 4.

1. **Третий тур в движке:** `data/tours/hr_clerk.json`, `hr_clerk` добавить в `TOUR_IDS` и в соответствие роль → тур. Стартовая страница — дашборд кадровика (`@start`). Режим автозапуска и демо-сотрудник берутся из страницы «Демо-тур» (`/admin/tour-settings`), как у остальных туров; в таблице «отдельным пользователям» кадровики показываются всегда, как руководители.
2. **Шаги** — по черновику, 12 карточек: приветствие, меню, сроки документов (`docs-expiry`), → реестр `?status=all&document_type_id=0`, реестр (`docs-table`), откуда берутся документы (первая строка «на проверке» — новый якорь `docs-pending`, нет такой строки — пропуск), карточка документа (кнопка «Открыть» в первой строке — новый якорь `docs-open`), проверка (кнопки статуса / массовая отметка — новый якорь `docs-verify`), → реестр демо-сотрудника, документы одного сотрудника, → договоры демо-сотрудника, договор (`contracts-create`), ходатайство (кнопка «Создать ходатайство» в строке демо-сотрудника — новый якорь `contracts-petition`), рекомендация (`contracts-recommendation`), «Что дальше» (одна плитка — уведомления МВД), финал. Шаги с демо-сотрудником пропускаются, если он не задан на странице «Демо-тур».
3. **Проверить правдивость двух шагов перед вводом текста.** Шаг «Карточка документа» говорит, что патент нельзя отметить проверенным без серии и номера бланка и профессии. Если это правило ещё не реализовано (в отчёте после П5 его нет — карточка патента получила четыре поля, но запрета на проверку без них не было), — **реализовать**: проверка патента (одиночная и массовая) отклоняется с понятным сообщением, какие поля пусты. Шаг «Ходатайство» про подбор адресата по месту работы — уже правда после справочника «Подразделения МВД».
4. **Шаг про карточки сотрудников (новый, после «Проверки»):** переход на `/hr/employees`, якорь на первой строке списка (`employees-first`), текст: «Здесь — все сотрудники. В карточке вы правите личные данные: ФИО, дату рождения, гражданство, должность — и добавляете документы. Роли, пароли и выплаты остаются у руководителя и экономиста.» Затем тур продолжает с реестра демо-сотрудника, как в черновике. Итого 13 карточек.
5. **Тесты:** `hr_clerk.json` валиден, у каждого шага-элемента якорь есть на странице под ролью `hr_clerk`; кадровик получает свой тур, а не тур руководителя; режим и демо-сотрудник берутся со страницы «Демо-тур»; без демо-сотрудника шаги с ним пропускаются.

## Демо-данные (владелец)
- Учётка с ролью «Кадровик».
- Хотя бы один документ «на проверке» — например, ещё один скан из кабинета Гаффурова.
- На странице «Демо-тур» для кадровика — «При каждом входе».

## Приёмка
Под кадровиком: тур стартует сам, 13 карточек, ни один шаг не указывает в пустоту; кадровик правит ФИО сотрудника в карточке, но не видит и не может поменять роль, пароль, ТМ и реквизиты выплат; патент без бланка не отмечается проверенным.
